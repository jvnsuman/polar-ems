# Evaluation: how good is it, and how do we know?

Reproduce every number here with one command:

```bash
python run_simulation.py          # about 90 s, prints both months and the combined summary
```

There is no automated regression guard yet (no tests in the repo).

## What is measured

| Metric | How |
| :-- | :-- |
| Diesel burned | Litres per 30 days for each controller, from the fuel curve (4.5 L/h + 0.235 L/kWh per running genset) |
| Saving | Percent versus the always-on baseline and versus the tuned rule controller |
| Genset-off hours | Hours with both gensets off |
| Unserved energy | Sum of the optimizer's `Puns` slack for executed steps (see caveat below) |
| CO2 avoided | (baseline litres minus POLAR EMS litres) x 2.68 kg/L |
| Solver | Number of MILP solves, mean solve time |

Controllers compared:

| Controller | Behaviour |
| :-- | :-- |
| Always-on baseline | Genset 1 every hour at `clamp(load + 4.17, 24, 80)` kW; wind and PV not used |
| Tuned rules | `RuleBasedFallbackController`: diesel-off when renewables and battery cover the load |
| POLAR EMS | Forecast, 24 h MILP, replan every 6 h or on a blizzard flag |

## The data, and its limits (read this before quoting a number)

- **Two synthetic 30-day months**: summer (seed 42) and polar night (seed 143), generated by `polar_ems/simulation/synthetic_data.py`. Blizzards, icing, load and weather are written by the authors.
- **No real station logs** were used. No ERA5, BSRN or Antarctic AWS backtest has been run.
- **The weather the optimizer sees is the true weather.** The benchmark passes actual wind speed, temperature and irradiance in as the forecast, and the blizzard flag triggers an immediate replan. Only load is genuinely forecast.
- **The load model trains on the first 96 h** and is then scored on a series that includes that window.
- **Unserved energy is the plan's own slack variable**, not shortfall measured against actual load.
- **The baseline does not use renewables.** Part of the saving is simply using wind and PV.

Treat every saving below as an upper bound.

## Realized-shortfall check (polar night, executed open loop)

I replayed the same plans against actual load and weather, with no real-time balancing step:

| Result | Value |
| :-- | --: |
| Shortfall energy | 3,668.6 kWh |
| Hours with shortfall above 0.5 kW | 417 of 720 |
| Load forecast MAPE (whole month) | 5.1% |
| Minimum-run violation | Yes, at hour 37 |

This shows the "0 kWh unserved" figure comes from the plan, not from execution. A real-time balancing layer (battery and genset trim to actual load) is needed before any unserved-energy claim.

## Known failure modes (what still goes wrong)

- **No forecast error model for weather**, so blizzard onset is perfectly anticipated in the benchmark.
- **Minimum run time is not carried across replans** (`initial_run_hours` is unused), so a genset started recently can be stopped at once.
- **No terminal SoC constraint**: each plan drains the battery by its end.
- **Deferrable load** needs 100 kWh in every 24 h window and can be pushed to the end of each window.
- **Last 24 h of each month** are not re-planned; the rule controller takes over.
- **Reserve ignores stored energy**: it counts full battery discharge power whatever the SoC.
- **Cold derating uses the horizon-average temperature**, which hides overnight lows.
- **Genset start wear** is only a fixed penalty; cold-start wear is not modelled.

## Ethics note

These metrics measure fuel and reserve behaviour in simulation. They say nothing about safety on a real station. No claim of life-support protection should be made until it is validated on station data with a shadow-mode pilot.
